## #330: deterministic verification mismatch

Issue → intake → classify → developer planning/generation → source review → sandbox precommit tests → saved draft. `verify.parse_review` checks met:true non-controller requirements for path/literal evidence. The review tried to certify the one-file restriction using evidence that did not satisfy that schema. `check_the_work` correctly refused source repairs without confirmed source defects, preserving no-product-code scope, but the review process never reached a valid conclusion. The underlying restriction can and should be proved by the exact changed-file set. Replacing one error string or requesting a larger review response does not fix the evidence type. Gaps001,003,042 are the systemic repair.

## #322: weak oracle, fragile edit protocol and unusable repair replies

Initial PR323's copied `isAnswered` test did not establish real review behavior. Later Fix run41097698325 generated a test importing nonexistent `review` (real export `reviewPR`); the sandbox rejected it. The recovered controller contains actual `read_file` calls for review-evidence.js and review.js, observed results, and consecutive invalid JSON replies. Its final state has actions=4, stop_reason=invalid_limit; this is not absence of tool execution. Raw replies were not retained, so truncation is a plausible historical cause (2000-token request observed), **not a proven exact root cause**. Current tool_reply cap=16384, parser accepts fenced/singleton object and export summaries exist on main. Their latest local tests pass, but #330 had zero repair actions and therefore does not live-validate the repair fix.

Tool output itself is clipped to3000 characters: #322's full-file reads omitted3983 and13640 characters respectively. The truncation flag is honest, but the next model must request focused ranges; increasing reply cap cannot recover omitted source automatically. Journal-driven source-range retrieval and evidence-change requirements address this with bounded context.

## Recovery state machine to implement incrementally

`accepted → planning → ready_to_act → action_claimed → observing → evaluating → verifying → completed`.

From observing/evaluating: transient transport/quota → `waiting_external(retryAt)`; invalid args/parse → `repair_protocol`; source/test failure → `diagnosing → selecting_new_strategy → ready_to_act`; missing authorization → `awaiting_approval`; missing external capability → `blocked/unsupported`; cancellation → `cancelling → cancelled`; interruption → `reconciling → prior safe state`.

Transition guards: exact goal/grant/candidate/engine identity; lease and monotonic journal sequence; no post-cancel new side effect; test success tied to candidate digest; completed requires every supported requirement plus deterministic policy/scope/publication proofs and independent validation. Provider failures never authorize source edits. Closed/superseded task is reconciled before inference. Owner approval answers must append a scoped event without erasing prior progress.

Each strategy retains number, failure category, hypothesis, evidence IDs, source digest, actions/receipts, normalized error, difference from previous strategy, next choice rationale, validation result, model/request usage and remaining budgets. Five meaningfully different repair strategies is a useful default ceiling, not a requirement to repeat an impossible action five times. Authentication denial stops pending authorization; quotas wait without consuming repair strategy; malformed arguments allow small bounded protocol retries; destructive side effects require idempotence or reconciliation before retry. Lifetime action/time/request bounds remain enforced across restarts.

Production proof for each repaired family: first run fixtures and fault-injection on exact source, then an explicitly owner-authorized disposable task, capture full receipts and objective terminal state, compare the previous failing case and a negative control. Never auto-merge or dispatch a production Fix as part of this audit.
