# Deletion retention and encrypted-vault compatibility — partial KF-AUDIT-026

The client silently kept only500 deleted-chat IDs on both deletion and sync merge. A stale offline replica could therefore restore an older deleted chat after the receipt was evicted. Failed localStorage writes were swallowed while deletion appeared successful. Startup also loaded a stale chat payload before applying already durable deletion receipts, so interruption between receipt and chat-list saves could resurrect a chat while offline.

Deletion receipts now remain for the vault's lifetime; storage limits are explicit, not eviction policies. Local deletion persists its receipt before removing the chat and refuses visibly if that fails. Sync merges the entire receipt union. Incoming receipt persistence failure hides deleted data in this session and stops before overwriting the cloud, with a visible stopped-sync error. Startup applies durable receipts before any export/sync. Existing encrypted280KB payload bounds remain: exhaustion preserves all receipts and the previous cloud snapshot, rather than silently deleting history to fit.

## Version fence and owner rollout decision

An old client would still clip receipts on its next deletion/merge. New snapshots therefore use envelopev2 with AES-GCM additional authenticated data binding that protocol. The actual baseline v1 reader rejects this version before any PUT; merely changing the envelope tov1 cannot decrypt the ciphertext. Updated readers still decrypt existingv1 backups, proven with a golden encrypted packet generated by the unchanged prior codec. New snapshots are alwaysv2, even before501 deletions, to fence legacy writers before they can introduce new loss. No server schema/key/secret change or automatic rewriting of stored owner data has occurred.

This is a client protocol migration proposal. Before any release/activation, the owner must approve its impact and upgrade all clients that need to sync. Old versions stop syncing instead of silently damaging deletion history. Existing passphrases and data are retained, but rolling back to a v1-only reader after v2 writes is unsafe/unusable. A safe rollback retains thev2 reader and receipt-preserving semantics, or temporarily uses read-only recovery. Never down-convert by dropping deletion receipts. No deployment/release/merge is authorized by this document.

## Limits

These are controlled replicas, not physical devices or a live user vault. Durable Object storage here is an in-memory fixture, not a claim about distributed transactions or production erasure. Export/erase/every-store retention, real device conflicts, genuine browser storage exhaustion and physical deletion remain open in026/041/046. Previously evicted legacy receipts cannot be recovered from nothing. Large receipt sets can reach existing explicit storage limits; compaction requires a separately designed acknowledgement/retirement protocol and cannot silently expire tombstones. No general memory, autonomy score or full026 closure is claimed.

Rollback before activation: withdraw/revise this unmerged candidate. After separately authorized activation, retainv2 decoding and deletion suppression during recovery; never deploy a v1-only client over migrated snapshots or reset accounting/owner data. Keep the golden codec/packet and historical failure evidence.
